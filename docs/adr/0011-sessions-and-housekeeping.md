# 0011. Сессии, фоновая уборка и поток кабинета

- Статус: принято
- Дата: 2026-11-11

## Контекст

После ADR 0009 и 0010 оставались открытыми: самодельные сессии виджета (каждая новая сессия — новый покупатель с отдельной квотой), access-токен, живущий 15 минут после выхода, отсутствие проверки заблокированного магазина, блокировка диалога на 600 секунд без продления, сообщения, остающиеся в буфере после падения воркера, бесконечный рост диалогов и памяти бота, опрос базы потоком кабинета каждые 1,5 секунды на вкладку.

## Решение

- Виджет: `POST /widget/{key}/session` выдаёт токен `id.подпись` (HMAC от `JWT_SECRET`), `WIDGET_SESSIONS_PER_IP_HOUR` на IP. Сообщения и поток принимают только подписанные токены; `widget.js` запрашивает сессию сам и перезапрашивает её при ответе 400.
- Access-токен получил `jti`; выход и окончание входа админа под магазином кладут его в `auth:revoked:*` до истечения срока. `current_user` проверяет отзыв и статус магазина: `suspended` → 403 `shop_suspended` (ставит `PUT /admin/tenants/{id}/status`), бот такого магазина не отвечает.
- Коды входа: `OTP_IP_REQUESTS` запросов кода с одного IP за 10 минут и втрое больше попыток проверки.
- Кука `satushy_session` (без данных, на весь сайт, срок как у refresh) — признак сессии для `src/proxy.ts`: без неё страницы кабинета сразу ведут на `/login?next=`. Страница входа с `next` сначала пробует обновить сессию, поэтому старые сессии без куки не требуют повторного входа.
- Блокировка диалога — 120 секунд с продлением каждые 40 (`keep_locked`). Cron `sweep_inbox` раз в 2 минуты ставит `flush_customer` для буферов, к которым 90 секунд никто не обращался.
- Cron `housekeeping` (раз в сутки): диалог без сообщений `CONVERSATION_IDLE_CLOSE_DAYS` (30) дней закрывается, песочница старше `SANDBOX_KEEP_DAYS` (7) удаляется, их чекпоинты стираются (`adelete_thread`), `search_log` хранится `SEARCH_LOG_KEEP_DAYS` (90) дней. Следующее сообщение покупателя открывает новый диалог: история остаётся в кабинете, память бота начинается заново.
- Cron `remind_leads`: заявка в статусе `new` старше `LEAD_REMINDER_HOURS` (2) часов — одно напоминание команде в Telegram.
- Поток кабинета ждёт сообщение в канале Redis `cabinet:<tenant>` (`app/core/poke.py`) и только потом читает базу; без сигнала проверяет раз в 5 секунд. `poke` вызывают ход бота, ответ менеджера, смена режима, заявки.
- Поисковые вызовы ML (эмбеддинг запроса, реранкер) — таймаут 15 секунд и один повтор; вектор запроса кэшируется в процессе на час. Реранкер не вызывается для запроса из 1–3 слов с точным совпадением артикула.
- В блок «Данные для ответа» добавлено текущее время магазина: бот знает день недели и час.

## Последствия

- Старые сессии виджета (без подписи) перестают приниматься: виджет получает новую, переписка в окне сохраняется из `localStorage`, но для бота это новый покупатель.
- На каждый запрос кабинета добавился один `EXISTS` в Redis и соединение с таблицей `tenants`.
- Не сделано: RLS для `agent_state` (пул чекпоинтера общий на все магазины, нужен свой слой поверх `AsyncPostgresSaver`), пропуск роутера на приветствиях (затрагивает около 20 тестов сценариев, выигрыш только на «привет»), Web Push при закрытой вкладке, онлайн-оплата, метрики и автоматические бэкапы (`make backup` — ручной дамп).
