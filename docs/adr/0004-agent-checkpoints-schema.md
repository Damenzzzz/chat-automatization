# 0004. Чекпоинты LangGraph в отдельной схеме без RLS

- Статус: принято
- Дата: 2026-11-04

## Контекст

Граф бота хранит состояние диалога через `AsyncPostgresSaver` (`langgraph-checkpoint-postgres`, psycopg 3), `thread_id = conversation_id`. Его таблицы (`checkpoints`, `checkpoint_blobs`, `checkpoint_writes`, `checkpoint_migrations`) создаёт сама библиотека: колонки `tenant_id` нет, схему таблиц мы не контролируем. Правило проекта — RLS на каждой таблице с `tenant_id`.

Роль приложения не может создавать таблицы в `public`, а `setup()` библиотеки делает `CREATE INDEX CONCURRENTLY`, который нельзя выполнить внутри транзакции миграции и который ждёт завершения всех открытых транзакций — в том числе транзакции самого Alembic.

## Решение

- Таблицы чекпоинтера живут в схеме `agent_state`. Миграция 0008 под владельцем БД в `autocommit_block()` создаёт схему, вызывает `PostgresSaver.setup()` и выдаёт роли приложения `USAGE` и `SELECT/INSERT/UPDATE/DELETE`.
- Приложение подключается к ним через пул psycopg с `search_path=agent_state`; `setup()` в рантайме не вызывается.
- RLS на этих таблицах нет. Доступ к чекпоинту есть только по `thread_id`, а `conversation_id` приложение получает после проверки RLS на `conversations` (`tenant_session`). В чекпоинте лежат сообщения диалога и найденные товары — те же данные, что в `messages`.

## Последствия

- Это осознанное исключение из правила «RLS на каждой таблице»: код не должен читать `agent_state` по чужому `thread_id` и не должен давать пользователю выбирать `thread_id` напрямую.
- Новая версия `langgraph-checkpoint-postgres` с новыми миграциями таблиц = новая ревизия Alembic, которая снова вызывает `setup_checkpointer`.
- При удалении диалога чекпоинты нужно чистить отдельно (`adelete_thread`) — сделать вместе с удалением данных клиента.
