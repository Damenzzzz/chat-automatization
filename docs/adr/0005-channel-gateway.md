# 0005. Шлюз каналов: буфер в Redis и ключи по каналу

- Статус: принято
- Дата: 2026-11-05

## Контекст

Вебхук обязан ответить сразу, сообщения одного покупателя за 1,5 секунды склеиваются, а Telegram и Meta повторяют доставку. Каждый магазин подключает свои ключи.

## Решение

- Текст сообщения лежит в списке Redis `inbox:{channel}:{sha256(customer)}`, в ARQ уходят только идентификаторы и номер `seq`. ARQ пишет аргументы задач в лог, поэтому текст и телефон покупателя в них не передаём.
- Склейка — скользящее окно: каждое сообщение увеличивает `seq` и ставит задачу с задержкой, задача выполняется, только если её `seq` последний.
- Доставка «хотя бы один раз»: буфер очищается после успешного хода, при падении задача повторяется до 3 раз, затем буфер снимается и уходит уведомление `turn_failed`. Повтор после падения в середине хода может продублировать сообщение покупателя в `messages`; потерять его хуже.
- Ключ дедупликации снимается, если не удалось поставить задачу: платформа повторит запрос.
- `phone_number_id`, `waba_id`, токен и `app_secret` зашифрованы Fernet целиком, в `channels.external_id` для уникальности лежит хеш номера. Канал до входа ищем SQL-функциями `channel_lookup` и `channel_by_public_key` (SECURITY DEFINER).
- Поток виджета — Redis Streams, а не pub/sub: ответ не теряется при обрыве, клиент продолжает с `Last-Event-ID`. Сессия передаётся заголовком через `fetch`, а не `EventSource`, чтобы не попадать в журналы доступа.

## Последствия

- У API обязателен `--timeout-graceful-shutdown`: иначе открытый поток виджета блокирует остановку и весь API на время до `SSE_MAX_SECONDS`.
- Лимиты виджета считаются по `request.client.host`: за обратным прокси нужен `uvicorn --proxy-headers`, иначе все покупатели делят один лимит IP.
- Проверка Origin защищает только от чужих сайтов в браузере; от прямых запросов защищают лимиты. Это важно, потому что ответы тратят баланс магазина.
